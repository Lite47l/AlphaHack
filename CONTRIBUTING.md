## Ветки

- `main` — версия для сдачи. Сюда попадает только проверенный `dev`; финальный коммит помечается тегом.
- `dev` — интеграционная ветка команды. Прямые коммиты в `dev` и `main` не делаем — только через PR.
- Рабочие ветки создаются от актуального `dev` и называются `<имя>/<ID задачи>-<кратко>`,
  например `liza/L05-payment-features`, `oleg/O04-rss`. Для работы по нескольким карточкам — `feat/<кратко>`.

## Коммиты

- Одна логическая правка — один коммит. Сообщение — по-английски или по-русски в повелительном наклонении,
  с ID задачи в начале или конце: `L05: aggregate payments by counterparty`.
- Не коммитим: `.env`, ключи, реальные CSV организаторов (`data/raw/`), производные профили (`data/generated/`),
  исходные PDF банка, архивы и `node_modules`. Это закрыто `.gitignore`, но при загрузке через веб-интерфейс GitHub
  `.gitignore` не действует — проверяйте список файлов перед отправкой.

## Pull request

1. Перед PR: `git fetch && git rebase origin/dev` (или merge), прогнать проверки своей части:
   - AI: `cd ai && pip install -r requirements-dev.txt && python -m pytest -q`
   - Go: `docker run --rm -v "$PWD":/src -w /src golang:1.27-alpine sh -c "go vet ./... && go test ./..."`
   - Frontend: `cd frontend && npm ci && npm run build`
   - Стек целиком: `docker compose up --build`, затем `./scripts/smoke_test.sh`
2. Заполнить шаблон PR (подставляется автоматически): ID карточки, что сделано, как проверено, ограничения.
3. Ревьюер — тот, кто указан в карточке в поле «Проверяет». Мерж в `dev` — после одобрения ревьюера.
4. В карточке оставить ссылку на PR и отметить выполненные пункты чек-листа. Карточку закрывает ревьюер после приёмки.

## Контракты

- Любое изменение полей API, инсайта, события или трассировки — сначала правка `docs/api_contract.md` в том же PR,
  с повышением версии контракта и упоминанием в описании PR. Олег и Арина предупреждаются до интеграции (T02).
- Новые поля добавляются как необязательные; удаление или переименование поля — только по согласованию.

## Данные и секреты

- Ключ LLM организаторов — только в локальном `.env` (шаблон — `.env.example`). Не вставлять в код, фронтенд,
  чаты и описания PR. При проблемах с доступом организаторам сообщаем название ключа и текст ошибки, не сам ключ.
- Обезличенные данные кейса и аналитика Альфа-Банка используются только в рамках кейса. Репозиторий остаётся
  приватным; доступ жюри — аккаунту `alfa-hack-2026` (T09).
- В карточки и PR не загружаем исходные данные и выгрузки с ними — только код, отчёты и ссылки на закрытое хранилище.

## Честность результатов

- Метрики приводим с размером выборки и оговорками (см. `docs/evaluation_report.md`).
- Моки и синтетические данные в интерфейсе и отчётах явно помечаются.
- На защите заявляем только то, что реализовано и проверено.
